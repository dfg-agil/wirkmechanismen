# Impact Model Generation Criteria (V5)

## General Rules
- **MANDATORY OUTPUT**: The completed Impact Model MUST be output as a JSON file in the project-required blueprint format, not only as prose or a conceptual draft.
- **NORMATIVE LANGUAGE**: `MUST`/`MANDATORY` are hard acceptance criteria; `MUST NOT`/`REJECT` are hard exclusion criteria; `SHOULD`/`RECOMMENDATION` are quality guidance; `MAY`/`ALLOWED` describes permitted alternatives; `EXPECTATION`, `GOAL`, and `RATIONALE` are explanatory only and are not acceptance criteria.
- References to figures are to be found in the source "Blessing_Chakrabarti_2009_DRM, a Design Research Methodology".
- Restrictions not explicitly mentioned apply as described in the source “Blessing_Chakrabarti_2009_DRM, a Design Research Methodology”. Neither the explicitly stated rules nor the implicit rules derived from the source “Blessing_Chakrabarti_2009_DRM, a Design Research Methodology” may be violated!
- No factors (whether influencing factors, success factors, etc.) may be made up. Only the factors present in the main model must be used. This rule must not be broken at any time. The "generated by AI" criteria described in section "0.1 Information" of the file "REFERENCE_MODEL_CRITERIA_V8.md" are excluded. Exception: support-driven new influencing factors are allowed only under the strict conditions defined in section 1.4.
- If, for some inexplicable reason, you do deviate from the rules or break them (whether consciously or unconsciously), make this transparently visible to the user at all times and explain why you did not adhere to the rules.
- Support MUST primarily be selected from the validated support packages and the package candidates MUST be scored. If no suitable package support exists, or an AI-generated Support is a better-scoring candidate for the described problem, an AI-generated Support MAY be selected and MUST be explicitly marked as `AI-generated support` in the IM. AI-generated Support is exempt from the Gatekeeping developer-confirmation rule for standalone IM generation, but it MUST obey the Main Model's factor labels and inherited factor-to-factor topology, directions, and established causal logic; its new Support edges MUST obey the IM rules below.

> Support selection source policy:
> 1. Primary source: validated support packages, if a package source is configured and available.
> 2. Fallback or alternative source: AI-generated support, if no package source is configured, the package source is unavailable, no package support matches the RM scope, or the AI-generated candidate is a better-scoring fit for the user's described problem.
> 3. AI-generated support is valid in fallback or alternative mode, but MUST be marked as AI-generated support and MUST include:
> - explicit target factor(s)
> - causal mechanism
> - measurable implementation metric (0, 0.5, 1.0)
> - validation plan
> 4. The derivation log MUST state which source path was used: package or fallback.

> Autonomous IM generation: For a user-described problem, the assistant MAY autonomously select and score package Supports and, where permitted above, AI-generated Supports. No intermediate developer validation of the assistant's Support proposal or new Support edges is required before the standalone IM JSON is produced. The resulting assumptions, scores, source path, and validation plans MUST be disclosed in the IM derivation log. This exception does not authorize changes to the Main Model.

## Overview

This document defines specific criteria for generating Impact Models in the Wirkmechanismen project. Impact Models build on validated Reference Models and model the desired future state after introducing support interventions.

## Core Principles

### Relationship to Reference Model
- **MANDATORY**: Each Impact Model MUST be derived from a validated Reference Model
- **MANDATORY**: Impact Model MUST use the same domain scope
- **MANDATORY**: The problem statement and all Success Factors remain identical to the validated Reference Model. The problem statement is model context, not a causal network element, unless the Reference Model explicitly contains a justified `Problem` element.
- **TRANSFORMATION**: Support elements (interventions) are added
- **TRANSFORMATION**: New or modified causal relationships are explicitly marked

## Structural Requirements

### 1. Element Taxonomy (MANDATORY)

#### 1.1 Support Elements (Interventions)
- **MANDATORY**: At least ONE (1) Support element per Impact Model
- **DEFINITION**: Concrete measures, tools, or interventions to improve Key Factors
- **CLASSIFICATION**: `"element type": "Support"`
- **MANDATORY**: Select at least 1 and no more than 3 Support elements per Key Factor. If the IM contains multiple Key Factors, each Key Factor MAY have its own set of 1-3 Supports.
- **REJECT**: Impact Models without Support elements

**Support Formulation**:
- **CORRECT**: `"Daily Moderation Guide"`, `"Visual Board"`, `"Timeboxing Timer"`
- **CORRECT**: Concrete tools, processes, or aids
- **WRONG**: Abstract goals or desired states

#### 1.2 Key Factor Preservation
- **MANDATORY**: All Key Factors from Reference Model MUST be adopted
- **CLASSIFICATION**: `"element type": "Schlüsselfaktor"` (Key Factor)
- **ROLE**: Primary intervention targets - influenced by Supports

#### 1.3 Success Factor Structure
- **MANDATORY**: All Success Factors from the Reference Model MUST be adopted
- **CLASSIFICATION**: `"element type": "Erfolgsfaktor"` (Success Factor) or `"Messbarer Erfolgsfaktor"` (Measurable Success Factor)
- **IMMUTABLE**: Success Factor definition remains identical to Reference Model

#### 1.4 Influencing Factors Adaptation
- **MANDATORY**: Influencing Factors from Reference Model are adopted
- **ALLOWED**: New Influencing Factors created by Supports
- **CLASSIFICATION**: `"element type": "Einflussfaktoren"` (Influencing Factors)
- **MANDATORY**: New Influencing Factors MUST be documented as support-driven assumptions `[A]` on every new incident causal connection.
- **MANDATORY (traceability)**: New Influencing Factors are only allowed if (1) they have at least one incoming and one outgoing causal connection, (2) they are causally linked to at least one Support and one inherited RM factor, and (3) the mechanism and measurement method are documented in `attributes.description`.

Here, "documented as `[A]`" means that every new incoming and outgoing causal
connection of the new factor carries `[A]`. The factor description MUST also
state the support mechanism, the measurement method, and the validation plan.
The new factor remains invalid if either the factor description or any required
incident connection is incomplete.

> Exception rule for new influencing factors:
> 1. Default rule: do not introduce new factors.
> 2. Exception is allowed only for support-driven influencing factors when all conditions are met:
> - at least one incoming and one outgoing causal connection
> - linked to at least one Support and at least one inherited RM factor
> - marked as assumption [A]
> - mechanism documented
> - measurement method documented
> - validation plan documented
> 3. If any condition is missing, the new factor is invalid and MUST be rejected.

### 2. Causal Network Structure (MANDATORY)

#### 2.1 Support-to-Key Factor Relationships
- **MANDATORY**: Each Support MUST influence at least one Key Factor
- **STRUCTURE**: `Support → Key Factor → [Influencing Factors] → Success Factor`
- **MANDATORY**: Support elements are **start nodes** (no incoming connections)
- **REJECT**: Supports without outgoing connections to Key Factors

#### 2.2 Modified Causal Relationships
- **MANDATORY**: Relationships changed by Supports MUST be documented
- **MECHANISM**:
  - **Option A**: Remove old connection, add new connection with `[A]`
  - **Option B**: Change connection strength/polarity and explain in `description`
- **MANDATORY**: Changes MUST be explained in connection `description`

#### 2.3 New Causal Relationships
- **ALLOWED**: Supports can create new causal relationships
- **MANDATORY**: All new connections MUST be marked with `[A]` (Assumption)
- **MANDATORY**: `description` MUST contain theoretical or empirical justification
- **SHOULD**: Validate assumptions through pilot projects or literature. The
  validation plan itself is nevertheless mandatory for every support-driven
  `[A]` connection.

#### 2.4 Path Requirements
- **MANDATORY**: At least one complete path from each selected Support → at least one Success Factor
- **MANDATORY**: Maximum path length: 5 connections (Support + 4 intermediate steps)
- **LOGIC CHECK**: All Supports MUST be causally connected to at least one Success Factor

#### 2.5 Deterministic IM derivation protocol (NEW, MANDATORY)

**Step 1 - Freeze inherited RM structure**
- Inherit all Key Factors, Success Factor(s), Measurable Success Factor(s), and Influencing Factors from the validated RM.
- Inherited RM nodes and inherited RM connections are immutable unless explicitly changed by a Support mechanism or unless the desired IM context requires a different causal statement. In both cases the deviation MUST be documented in the IM change log; the changed edge MUST be marked `[A]` until validated.

> Inherited loop handling:
> 1. Feedback loops inherited from the RM may remain in the IM if they are unchanged and still causally valid.
> 2. If an inherited loop is modified by support intervention, all modified edges MUST be marked [A] and include mechanism plus validation plan.
> 3. IM end-node checks apply to newly introduced support-driven paths and must not force deletion of causally valid inherited RM dynamics.

**Step 2 - Support candidate extraction**
- Build support candidate set from controllable leverage points that directly target:
  1. primary Key Factor, then
  2. first-hop Influencing Factors on valid RM Key→Success paths.
- Supports that restate outcomes (instead of interventions) are invalid.

**Step 3 - Support scoring**
Package Supports are the first candidate pool and MUST be scored when a package
source is configured and available. If no package Support matches the RM scope,
or an AI-generated Support is a better fit for the user's described problem,
AI-generated Support candidates MUST also be scored using the same criteria.
- Score each support candidate with deterministic criteria:
  - +3 directly actionable by the team
  - +2 mechanism to target factor is concrete and falsifiable
  - +2 implementation state is measurable with discrete scale (0, 0.5, 1.0)
  - -2 mostly dependent on external actors
  - -2 duplicates an already selected support without distinct mechanism
- Select the top 1-3 Supports for each Key Factor. Package Supports are scored first; AI-generated Supports are also scored when no suitable package Support exists or when an AI-generated candidate scores better for the described problem. The selected source path and the scores of all considered candidates MUST be logged.
- Tie-breakers (strict order):
  1. higher mechanism specificity (clearer causal action verb + target factor)
  2. shorter average path length to Success Factor(s)
  3. higher influenceability of targeted factor(s)
  4. alphabetical label

> Deterministic scoring interpretation:
> 1. Directly actionable by team:
> - 1.0 if the team can implement without external dependency
> - 0.5 if partial external dependency exists
> - 0.0 if mainly external dependency
> 2. Mechanism specificity:
> - 1.0 if mechanism states clear action, target factor, and expected direction
> - 0.5 if one of these components is missing
> - 0.0 if mechanism is abstract or goal-like
> 3. Measurable implementation state:
> - 1.0 if a concrete binary or numeric metric is defined
> - 0.5 if only qualitative metric is defined
> - 0.0 if no measurable metric is defined
> 4. Duplicate support penalty applies if proposed support targets the same factor(s) with no distinct mechanism statement.
> 5. All scoring inputs and final score MUST be logged per support candidate.

> Tie tolerance:
> If two support candidates differ by at most 0.01 in total score, apply tie-breakers in listed order.
> If still tied after all tie-breakers, select alphabetical label.
> The full tie-break trace MUST be documented in the IM derivation log.

**Step 4 - New/modified edge rule**
- Every support-driven new or modified edge MUST be marked `[A]` until validated.
- Each such edge MUST include mechanism, expected directional change, and validation plan in `attributes.description`.

**Step 5 - Minimal path preservation**
- After support insertion and connection updates, at least one complete path from each Support to at least one Success Factor must remain.
- Removing any selected Support must reduce at least one intended improvement path; otherwise support distinctness is not satisfied.

### 3. Source Attribution (MANDATORY)

#### 3.1 Literature and Evidence (from Reference Model)
- **INHERITED**: Literature sources `[1]`, `[2]`, etc. from Reference Model remain unchanged
- **MANDATORY**: Source attribution for unchanged connections remains identical

#### 3.2 Assumptions for Interventions (Priority for new connections)
- **MANDATORY**: All new connections (through Supports) MUST be marked as `[A]` (Assumption)
- **MANDATORY**: `description` MUST contain at least one applicable justification of the assumption:
  - Theoretical foundation (design principles, methodology)
  - Empirical evidence (pilot projects, expert opinions)
  - Analogies to similar interventions
- **GOAL**: Transform assumptions into evidence through incremental validation

#### 3.3 Validated Interventions (after piloting)
- **ALLOWED**: After successful piloting, replace `[A]` with `[O]` (own investigation)
- **ALLOWED**: With literature evidence, replace `[A]` with `[1-9]+`
- **MANDATORY**: Document validation process in commit message

#### 3.4 Inadmissible Sources
- **REJECT**: Connections with `[?]` (unknown source)
- **REJECT**: New connections without source attribution (even if assumption)

### 3.5 Validation planning and derivation trace
- A **validation plan** is a future empirical check, not proof that the
  assumption has already been validated. For each support-driven `[A]` edge it
  MUST state: the measure or observation, the data source or test setting, the
  expected directional result, the responsible validation activity, the planned
  timing, and the criterion for changing `[A]` to `[O]` or a literature source.
- **Validation Planning: 100%** means:
  `number of support-driven [A] edges with a complete validation plan /
  total number of support-driven [A] edges * 100`.
  The result MUST be 100. An `[A]` edge without a complete plan is invalid.
- The IM derivation log records why the selected Supports were chosen and makes
  the result reproducible. It MUST be stored as the companion JSON file
  `{impact-model-name}-derivation-log.json` next to the IM blueprint and MUST
  contain: RM source and validation status, candidate source path, all scored
  candidates, scores, tie-breaks, selected Supports per Key Factor, inherited
  and changed edges, and the support-distinctness/path checks.

### 4. Measurability and Influenceability Criteria

#### 4.1 Support Properties
- **MANDATORY**: The Support implementation degree MUST be represented by a measurable discrete value `0`, `0.5`, or `1.0`; influenceability SHOULD be `1.0` and any lower value MUST be explained by an external dependency.
- **RATIONALE**: Interventions are under direct team control
- **DOCUMENTATION**: Support implementation degree MUST be measurable (e.g., "Board present: yes/no", "Guide usage rate")

#### 4.2 Key Factor Changes
- **HYPOTHESIS**: Supports improve Key Factors
- **MANDATORY**: Expected improvement MUST be described in Support connection
- **MEASURABILITY**: Key Factor measurability remains identical (from Reference Model)
- **INFLUENCEABILITY**: Can increase if Support creates direct control option

#### 4.3 Success Factor Invariance
- **MANDATORY**: Success Factor measurability and influenceability remain unchanged
- **RATIONALE**: Long-term goals don't change through short-term interventions

### 5. Connection Semantics

#### 5.0 Context-sensitive polarity handling (new in V3)
- **MANDATORY**: Impact Models MUST reflect the desired post-intervention situation they represent. The desired context MUST be derived from the problem statement, the intended support logic, and the expected improvement path, and the causal links MUST reflect that context.
- **MANDATORY**: The polarity of IM links MUST be chosen based on whether the link accurately represents that desired context, not by mechanically copying the Main Model.
- **ALLOWED**: If a Main Model connection is already source-supported and its polarity still accurately represents the IM context, it MAY be adopted unchanged.
- **MANDATORY**: If the Main Model polarity would misrepresent the IM context, the IM connection MUST be revised to fit the desired situation and the rationale documented.
- **MANDATORY**: IM connections that deviate from the Main Model polarity for context reasons MUST include a short explanation in `description` or the IM derivation log.


#### 5.1 Direction and Polarity
- **MANDATORY**: All connections MUST be directed (`"direction": "directed"`)
- **MANDATORY**: Connection type MUST use DRM polarities (`++`, `+-`, `-+`, `--`)
- **MANDATORY**: RM and IM polarity MUST reflect the model context they represent: RM = current/observed situation; IM = desired/post-intervention situation.
- **ALLOWED**: If a Main Model connection is already source-supported and its polarity still accurately represents the RM/IM context, it MAY be adopted unchanged.
- **MANDATORY**: If the Main Model polarity would misrepresent the RM/IM context, the RM/IM connection MUST be revised to fit the relevant context and the rationale documented.
- **MANDATORY**: Support → Key Factor connections MUST use `++` unless the intended mechanism requires another polarity; any other polarity MUST be justified in `description` or the IM derivation log.

#### 5.2 Connection Descriptions for Supports
- **MANDATORY**: Support connections MUST explain causal mechanism
- **FORMAT**: "Support X improves Factor Y through Mechanism Z"
- **LENGTH**: 30-200 words for new assumption-based connections
- **CONTENT**:
  - How does the support work?
  - Why should it improve the factor?
  - What assumptions underlie this?

## Validation Steps

### Automatic Validation
1. JSON schema compliance (`lint_blueprint.py`)
2. Element/connection ID uniqueness
3. Reference integrity (from/to reference existing IDs)
4. Factor taxonomy compliance (including Support elements)
5. **Support Validation**: At least one Support present
6. **Topology Validation**: Supports as start nodes; Success Factor as end node for newly introduced support-driven paths. Inherited RM loops may remain if they are unchanged and causally valid.
7. **Deterministic Trace Validation**:
  - support scoring table present
  - tie-break trace complete
  - support distinctness check documented
8. **Assumption Trace Validation**:
  - all new/modified support-driven edges marked `[A]`
  - each `[A]` edge contains mechanism + directional expectation + validation plan

### Content Validation
1. **Reference Model Consistency**: Problem statement and all Success Factors identical to Reference Model
2. **Support Integration**: All Supports connected to Key Factors
3. **Path Completeness**: Each selected Support has a path to at least one Success Factor
4. **Assumption Documentation**: All `[A]` connections have meaningful descriptions
5. **Validation Plan**: Each assumption has planned validation mechanism
6. **Minimal Path Preservation**: Support distinctness and intended improvement paths remain valid after pruning check

### Quality Metrics
- **Support Coverage**: 100% - All Key Factors addressed by at least one Support
- **Assumption Documentation**: 100% - All `[A]` connections have justification
- **Topological Integrity**: 100% - Supports (start) → at least one Success Factor (end) structure
- **Path Completeness**: 100% - At least one complete path present
- **Validation Planning**: 100% of support-driven `[A]` connections have a complete validation plan, as defined in section 3.5
- **Deterministic Traceability**: 100% - support scoring, tie-break decisions, and change log are reproducible

## Compliance Checklist

### Pre-Submission
- [ ] Based on validated Reference Model (identical domain scope)
- [ ] Problem statement and all Success Factors adopted from Reference Model
- [ ] At least 1 Support element present
- [ ] All Supports connected to Key Factors
- [ ] Each selected Support has a complete causal path to at least one Success Factor
- [ ] All new connections marked with `[A]`
- [ ] All `[A]` connections have justification in `description`
- [ ] All `[A]` support-driven edges include mechanism + directional expectation + validation plan
- [ ] Supports defined as start nodes (no incoming connections)
- [ ] Measurability/influenceability values consistent
- [ ] JSON validation successful
- [ ] Companion JSON IM derivation log is present (support candidates, scores, tie-break trace, selected supports)
- [ ] Support distinctness check is documented
- [ ] Minimal path preservation check is documented

### Review Criteria
- [ ] Support interventions are concrete and implementable
- [ ] Causal mechanisms scientifically/practically plausible
- [ ] Assumption justifications comprehensible
- [ ] Validation plans present for assumptions
- [ ] No contradictory causal relationships to Reference Model
- [ ] Model complexity appropriate (not too many Supports)
- [ ] Re-running with same inputs and scoring rules yields same selected supports

### Validation Planning
- [ ] For each `[A]` connection: validation method defined
- [ ] Pilot timeline created
- [ ] Success criteria for intervention defined
- [ ] Data collection mechanisms specified

## Rejection Criteria

- **AUTOMATIC REJECT**: No Support element present
- **AUTOMATIC REJECT**: Supports not connected to Key Factors
- **AUTOMATIC REJECT**: Any selected Support lacks a complete causal chain to at least one Success Factor
- **AUTOMATIC REJECT**: New connections without `[A]` marking
- **AUTOMATIC REJECT**: `[A]` connections without justification in `description`
- **AUTOMATIC REJECT**: JSON schema violations
- **AUTOMATIC REJECT**: Success Factor changed compared to Reference Model
- **AUTOMATIC REJECT**: Missing or incomplete IM derivation log
- **AUTOMATIC REJECT**: Missing support scoring/tie-break trace
- **AUTOMATIC REJECT**: Missing validation plan in support-driven `[A]` edges

## Incremental Validation and Integration

### Validation Workflow
1. **Impact Model Scaffolding**: Initial model with `[A]` assumptions
2. **Human + Peer Review**: Plausibility check
3. **Piloting**: Small test group, collect qualitative evidence
4. **Iteration**: `[A]` → `[O]` for validated assumptions
5. **Scaling**: Quantitative validation, possibly `[O]` → `[1-9]+` if published
6. **Integration**: Integrate validated Support relationships into Main Model

### Commit-based Tracking
- **INITIAL**: `[IMPACT] Add {domain} impact model with {N} support interventions`
- **VALIDATION**: `[IMPACT] Validate assumption [A] → [O] for {connection} based on {pilot/study}`
- **ITERATION**: `[IMPACT] Refine support {name} based on pilot results`
- **FINALIZATION**: `[IMPACT] Promote validated {domain} model to production`

## Summary

Impact Models are future-state models that build on validated Reference Models. They:
1. Introduce **Support elements** (concrete interventions)
2. Document **new causal relationships** as **assumptions** `[A]`
3. Retain the **problem statement and all Success Factors** from the Reference Model
4. Follow an **incremental validation cycle**
5. Feed validated findings back into the **Main Model**

Impact Models are experimental in nature and enable systematic testing of design interventions with clear evidence basis.
