  10: ## Overview
  11: 
  12: This document defines specific criteria for generating Impact Models in the Wirkmechanismen project. Impact Models build on validated Reference Models and model the desired future state after introducing support interventions.
  13: 
  14: ## Core Principles
  15: 
  16: ### Relationship to Reference Model
  17: - **MANDATORY**: Each Impact Model MUST be derived from a validated Reference Model
  18: - **MANDATORY**: Impact Model MUST use the same domain scope
  19: - **MANDATORY**: Problem and Success Factor remain identical
  20: - **TRANSFORMATION**: Support elements (interventions) are added
  21: - **TRANSFORMATION**: New or modified causal relationships are explicitly marked
  22: 
  23: ## Structural Requirements
  24: 
  25: ### 1. Element Taxonomy (MANDATORY)
  26: 
  27: #### 1.1 Support Elements (Interventions)
  28: - **MANDATORY**: At least ONE (1) Support element per Impact Model
  29: - **DEFINITION**: Concrete measures, tools, or interventions to improve Key Factors
  30: - **CLASSIFICATION**: `"element type": "Support"`
  31: - **RECOMMENDATION**: 1-3 Support elements for focused interventions
  32: - **REJECT**: Impact Models without Support elements
  33: 
  34: **Support Formulation**:
  35: - **CORRECT**: `"Daily Moderation Guide"`, `"Visual Board"`, `"Timeboxing Timer"`
  36: - **CORRECT**: Concrete tools, processes, or aids
  37: - **WRONG**: Abstract goals or desired states
  38: 
  39: #### 1.2 Key Factor Preservation
  40: - **MANDATORY**: All Key Factors from Reference Model MUST be adopted
  41: - **CLASSIFICATION**: `"element type": "SchlÃ¼sselfaktor"` (Key Factor)
  42: - **ROLE**: Primary intervention targets - influenced by Supports
  43: 
  44: #### 1.3 Success Factor Structure
  45: - **MANDATORY**: Success Factor from Reference Model MUST be adopted
  46: - **CLASSIFICATION**: `"element type": "Erfolgsfaktor"` (Success Factor) or `"Messbarer Erfolgsfaktor"` (Measurable Success Factor)
  47: - **IMMUTABLE**: Success Factor definition remains identical to Reference Model
  48: 
  49: #### 1.4 Influencing Factors Adaptation
  50: - **MANDATORY**: Influencing Factors from Reference Model are adopted
  51: - **ALLOWED**: New Influencing Factors created by Supports
  52: - **CLASSIFICATION**: `"element type": "Einflussfaktoren"` (Influencing Factors)
  53: - **MANDATORY**: New Influencing Factors MUST be documented as assumptions `[A]`
  54: - **MANDATORY (traceability)**: New Influencing Factors are only allowed if (1) they are causally linked to at least one Support and one inherited RM factor, and (2) the mechanism and measurement method are documented in `attributes.description`.
  55: 
  56: ### 2. Causal Network Structure (MANDATORY)
  57: 
  58: #### 2.1 Support-to-Key Factor Relationships
  59: - **MANDATORY**: Each Support MUST influence at least one Key Factor
  60: - **STRUCTURE**: `Support â†’ Key Factor â†’ [Influencing Factors] â†’ Success Factor`
  61: - **MANDATORY**: Support elements are **start nodes** (no incoming connections)
  62: - **REJECT**: Supports without outgoing connections to Key Factors
  63: 
  64: #### 2.2 Modified Causal Relationships
  65: - **MANDATORY**: Relationships changed by Supports MUST be documented
  66: - **MECHANISM**:
  67:   - **Option A**: Remove old connection, add new connection with `[A]`
  68:   - **Option B**: Change connection strength/polarity and explain in `description`
  69: - **MANDATORY**: Changes MUST be explained in connection `description`
  70: 
  71: #### 2.3 New Causal Relationships
  72: - **ALLOWED**: Supports can create new causal relationships
  73: - **MANDATORY**: All new connections MUST be marked with `[A]` (Assumption)
  74: - **MANDATORY**: `description` MUST contain theoretical or empirical justification
  75: - **RECOMMENDATION**: Validate assumptions through pilot projects or literature
  76: 
  77: #### 2.4 Path Requirements
  78: - **MANDATORY**: At least one complete path from Support â†’ Success Factor
  79: - **MANDATORY**: Maximum path length: 5 connections (Support + 4 intermediate steps)
  80: - **LOGIC CHECK**: All Supports MUST be causally connected to Success Factor
  81: 
  82: #### 2.5 Deterministic IM derivation protocol (NEW, MANDATORY)
  83: 
  84: **Step 1 - Freeze inherited RM structure**
  85: - Inherit all Key Factors, Success Factor(s), Measurable Success Factor(s), and Influencing Factors from the validated RM.
  86: - Inherited RM nodes and inherited RM connections are immutable unless explicitly changed by a Support mechanism and documented in the IM change log.
  87: 
  88: **Step 2 - Support candidate extraction**
  89: - Build support candidate set from controllable leverage points that directly target:
  90:   1. primary Key Factor, then
  91:   2. first-hop Influencing Factors on valid RM Keyâ†’Success paths.
  92: - Supports that restate outcomes (instead of interventions) are invalid.
  93: 
  94: **Step 3 - Support scoring**
  95: Ideally, a measure should be selected and evaluated directly from a suitable support package (if one is available). If no suitable measure exists, then "AI-generated support" applies:
  96: - Score each support candidate with deterministic criteria:
  97:   - +3 directly actionable by the team
  98:   - +2 mechanism to target factor is concrete and falsifiable
  99:   - +2 implementation state is measurable with discrete scale (0, 0.5, 1.0)
 100:   - -2 mostly dependent on external actors
 101:   - -2 duplicates an already selected support without distinct mechanism
 102: - Select top 1-3 supports.
 103: - Tie-breakers (strict order):
 104:   1. higher mechanism specificity (clearer causal action verb + target factor)
 105:   2. shorter average path length to Success Factor(s)
 106:   3. higher influenceability of targeted factor(s)
 107:   4. alphabetical label
 108: 
 109: **Step 4 - New/modified edge rule**
 110: - Every support-driven new or modified edge MUST be marked `[A]` until validated.
 111: - Each such edge MUST include mechanism, expected directional change, and validation plan in `attributes.description`.
 112: 
 113: **Step 5 - Minimal path preservation**
 114: - After support insertion and connection updates, at least one complete path from each Support to at least one Success Factor must remain.
 115: - Removing any selected Support must reduce at least one intended improvement path; otherwise support distinctness is not satisfied.
 116: 
 117: ### 3. Source Attribution (MANDATORY)
 118: 
 119: #### 3.1 Literature and Evidence (from Reference Model)
 120: - **INHERITED**: Literature sources `[1]`, `[2]`, etc. from Reference Model remain unchanged
 121: - **MANDATORY**: Source attribution for unchanged connections remains identical
 122: 
 123: #### 3.2 Assumptions for Interventions (Priority for new connections)
 124: - **MANDATORY**: All new connections (through Supports) MUST be marked as `[A]` (Assumption)
 125: - **MANDATORY**: `description` MUST contain justification of assumption:
 126:   - Theoretical foundation (design principles, methodology)
 127:   - Empirical evidence (pilot projects, expert opinions)
 128:   - Analogies to similar interventions
 129: - **GOAL**: Transform assumptions into evidence through incremental validation
 130: 
 131: #### 3.3 Validated Interventions (after piloting)
 132: - **ALLOWED**: After successful piloting, replace `[A]` with `[O]` (own investigation)
 133: - **ALLOWED**: With literature evidence, replace `[A]` with `[1-9]+`
 134: - **MANDATORY**: Document validation process in commit message
 135: 
 136: #### 3.4 Inadmissible Sources
 137: - **REJECT**: Connections with `[?]` (unknown source)
 138: - **REJECT**: New connections without source attribution (even if assumption)
 139: 
 140: ### 4. Measurability and Influenceability Criteria
 141: 
 142: #### 4.1 Support Properties
 143: - **EXPECTATION**: Supports have high influenceability (= 1.0)
 144: - **RATIONALE**: Interventions are under direct team control
 145: - **EXPECTATION**: Supports have measurable implementation state using discrete scale values (0, 0.5, 1.0)
 146: - **DOCUMENTATION**: Support implementation degree MUST be measurable (e.g., "Board present: yes/no", "Guide usage rate")
 147: 
 148: #### 4.2 Key Factor Changes
 149: - **HYPOTHESIS**: Supports improve Key Factors
 150: - **MANDATORY**: Expected improvement MUST be described in Support connection
 151: - **MEASURABILITY**: Key Factor measurability remains identical (from Reference Model)
 152: - **INFLUENCEABILITY**: Can increase if Support creates direct control option
 153: 
 154: #### 4.3 Success Factor Invariance
 155: - **MANDATORY**: Success Factor measurability and influenceability remain unchanged
 156: - **RATIONALE**: Long-term goals don't change through short-term interventions
 157: 
 158: ### 5. Connection Semantics
 159: 
 160: #### 5.1 Direction and Polarity
 161: - **MANDATORY**: All connections MUST be directed (`"direction": "directed"`)
 162: - **MANDATORY**: Connection type MUST use DRM polarities (`++`, `+-`, `-+`, `--`)
 163: - **EXPECTATION**: Support â†’ Key Factor connections are typically positive (`++`)
 164: 
 165: #### 5.2 Connection Descriptions for Supports
 166: - **MANDATORY**: Support connections MUST explain causal mechanism
 167: - **FORMAT**: "Support X improves Factor Y through Mechanism Z"
 168: - **LENGTH**: 30-200 words for new assumption-based connections
 169: - **CONTENT**:
 170:   - How does the support work?
 171:   - Why should it improve the factor?
 172:   - What assumptions underlie this?

 174: ## Validation Steps
 175: 
 176: ### Automatic Validation
 177: 1. JSON schema compliance (`lint_blueprint.py`)
 178: 2. Element/connection ID uniqueness
 179: 3. Reference integrity (from/to reference existing IDs)
 180: 4. Factor taxonomy compliance (including Support elements)
 181: 5. **Support Validation**: At least one Support present
 182: 6. **Topology Validation**: Supports as start nodes, Success Factor as end node
 183: 7. **Deterministic Trace Validation**:
 184:   - support scoring table present
 185:   - tie-break trace complete
 186:   - support distinctness check documented
 187: 8. **Assumption Trace Validation**:
 188:   - all new/modified support-driven edges marked `[A]`
 189:   - each `[A]` edge contains mechanism + directional expectation + validation plan
 190: 
 191: ### Content Validation
 192: 1. **Reference Model Consistency**: Problem/Success Factor identical to Reference Model
 193: 2. **Support Integration**: All Supports connected to Key Factors
 194: 3. **Path Completeness**: At least one path Support â†’ Success Factor
 195: 4. **Assumption Documentation**: All `[A]` connections have meaningful descriptions
 196: 5. **Validation Plan**: Each assumption has planned validation mechanism
 197: 6. **Minimal Path Preservation**: Support distinctness and intended improvement paths remain valid after pruning check
 198: 
 199: ### Quality Metrics

 253: ## Incremental Validation and Integration
 254: 
 255: ### Validation Workflow
 256: 1. **Impact Model Scaffolding**: Initial model with `[A]` assumptions
 257: 2. **Human + Peer Review**: Plausibility check
 258: 3. **Piloting**: Small test group, collect qualitative evidence
 259: 4. **Iteration**: `[A]` â†’ `[O]` for validated assumptions
 260: 5. **Scaling**: Quantitative validation, possibly `[O]` â†’ `[1-9]+` if published
 261: 6. **Integration**: Integrate validated Support relationships into Main Model

 269: ## Summary
 270: 
 271: Impact Models are future-state models that build on validated Reference Models. They:
 272: 1. Introduce **Support elements** (concrete interventions)
 273: 2. Document **new causal relationships** as **assumptions** `[A]`
 274: 3. Retain **Problem and Success Factor** from Reference Model
 275: 4. Follow an **incremental validation cycle**
 276: 5. Feed validated findings back into the **Main Model**
 277: 
 278: Impact Models are experimental in nature and enable systematic testing of design interventions with clear evidence basis.
