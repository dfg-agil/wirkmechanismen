  20: ## Overview
  21: 
  22: This document defines specific criteria for generating Impact Models in the Wirkmechanismen project. Impact Models build on validated Reference Models and model the desired future state after introducing support interventions.
  23: 
  24: ## Core Principles
  25: 
  26: ### Relationship to Reference Model
  27: - **MANDATORY**: Each Impact Model MUST be derived from a validated Reference Model
  28: - **MANDATORY**: Impact Model MUST use the same domain scope
  29: - **MANDATORY**: Problem and Success Factor remain identical
  30: - **TRANSFORMATION**: Support elements (interventions) are added
  31: - **TRANSFORMATION**: New or modified causal relationships are explicitly marked
  32: 
  33: ## Structural Requirements
  34: 
  35: ### 1. Element Taxonomy (MANDATORY)
  36: 
  37: #### 1.1 Support Elements (Interventions)
  38: - **MANDATORY**: At least ONE (1) Support element per Impact Model
  39: - **DEFINITION**: Concrete measures, tools, or interventions to improve Key Factors
  40: - **CLASSIFICATION**: `"element type": "Support"`
  41: - **RECOMMENDATION**: 1-3 Support elements for focused interventions
  42: - **REJECT**: Impact Models without Support elements
  43: 
  44: **Support Formulation**:
  45: - **CORRECT**: `"Daily Moderation Guide"`, `"Visual Board"`, `"Timeboxing Timer"`
  46: - **CORRECT**: Concrete tools, processes, or aids
  47: - **WRONG**: Abstract goals or desired states
  48: 
  49: #### 1.2 Key Factor Preservation
  50: - **MANDATORY**: All Key Factors from Reference Model MUST be adopted
  51: - **CLASSIFICATION**: `"element type": "SchlÃ¼sselfaktor"` (Key Factor)
  52: - **ROLE**: Primary intervention targets - influenced by Supports
  53: 
  54: #### 1.3 Success Factor Structure
  55: - **MANDATORY**: Success Factor from Reference Model MUST be adopted
  56: - **CLASSIFICATION**: `"element type": "Erfolgsfaktor"` (Success Factor) or `"Messbarer Erfolgsfaktor"` (Measurable Success Factor)
  57: - **IMMUTABLE**: Success Factor definition remains identical to Reference Model
  58: 
  59: #### 1.4 Influencing Factors Adaptation
  60: - **MANDATORY**: Influencing Factors from Reference Model are adopted
  61: - **ALLOWED**: New Influencing Factors created by Supports
  62: - **CLASSIFICATION**: `"element type": "Einflussfaktoren"` (Influencing Factors)
  63: - **MANDATORY**: New Influencing Factors MUST be documented as assumptions `[A]`
  64: - **MANDATORY (traceability)**: New Influencing Factors are only allowed if (1) they are causally linked to at least one Support and one inherited RM factor, and (2) the mechanism and measurement method are documented in `attributes.description`.
  65: 
  66: > Exception rule for new influencing factors:
  67: > 1. Default rule: do not introduce new factors.
  68: > 2. Exception is allowed only for support-driven influencing factors when all conditions are met:
  69: > - linked to at least one Support and at least one inherited RM factor
  70: > - marked as assumption [A]
  71: > - mechanism documented
  72: > - measurement method documented
  73: > - validation plan documented
  74: > 3. If any condition is missing, the new factor is invalid and MUST be rejected.
  75: 
  76: ### 2. Causal Network Structure (MANDATORY)
  77: 
  78: #### 2.1 Support-to-Key Factor Relationships
  79: - **MANDATORY**: Each Support MUST influence at least one Key Factor
  80: - **STRUCTURE**: `Support â†’ Key Factor â†’ [Influencing Factors] â†’ Success Factor`
  81: - **MANDATORY**: Support elements are **start nodes** (no incoming connections)
  82: - **REJECT**: Supports without outgoing connections to Key Factors
  83: 
  84: #### 2.2 Modified Causal Relationships
  85: - **MANDATORY**: Relationships changed by Supports MUST be documented
  86: - **MECHANISM**:
  87:   - **Option A**: Remove old connection, add new connection with `[A]`
  88:   - **Option B**: Change connection strength/polarity and explain in `description`
  89: - **MANDATORY**: Changes MUST be explained in connection `description`
  90: 
  91: #### 2.3 New Causal Relationships
  92: - **ALLOWED**: Supports can create new causal relationships
  93: - **MANDATORY**: All new connections MUST be marked with `[A]` (Assumption)
  94: - **MANDATORY**: `description` MUST contain theoretical or empirical justification
  95: - **RECOMMENDATION**: Validate assumptions through pilot projects or literature
  96: 
  97: #### 2.4 Path Requirements
  98: - **MANDATORY**: At least one complete path from Support â†’ Success Factor
  99: - **MANDATORY**: Maximum path length: 5 connections (Support + 4 intermediate steps)
 100: - **LOGIC CHECK**: All Supports MUST be causally connected to Success Factor
 101: 
 102: #### 2.5 Deterministic IM derivation protocol (NEW, MANDATORY)
 103: 
 104: **Step 1 - Freeze inherited RM structure**
 105: - Inherit all Key Factors, Success Factor(s), Measurable Success Factor(s), and Influencing Factors from the validated RM.
 106: - Inherited RM nodes and inherited RM connections are immutable unless explicitly changed by a Support mechanism and documented in the IM change log.
 107: 
 108: > Inherited loop handling:
 109: > 1. Feedback loops inherited from the RM may remain in the IM if they are unchanged and still causally valid.
 110: > 2. If an inherited loop is modified by support intervention, all modified edges MUST be marked [A] and include mechanism plus validation plan.
 111: > 3. IM end-node checks apply to newly introduced support-driven paths and must not force deletion of causally valid inherited RM dynamics.
 112: 
 113: **Step 2 - Support candidate extraction**
 114: - Build support candidate set from controllable leverage points that directly target:
 115:   1. primary Key Factor, then
 116:   2. first-hop Influencing Factors on valid RM Keyâ†’Success paths.
 117: - Supports that restate outcomes (instead of interventions) are invalid.
 118: 
 119: **Step 3 - Support scoring**
 120: Ideally, a measure should be selected and evaluated directly from a suitable support package (if one is available). If no suitable measure exists, then "AI-generated support" applies:
 121: - Score each support candidate with deterministic criteria:
 122:   - +3 directly actionable by the team
 123:   - +2 mechanism to target factor is concrete and falsifiable
 124:   - +2 implementation state is measurable with discrete scale (0, 0.5, 1.0)
 125:   - -2 mostly dependent on external actors
 126:   - -2 duplicates an already selected support without distinct mechanism
 127: - Select top 1-3 supports.
 128: - Tie-breakers (strict order):
 129:   1. higher mechanism specificity (clearer causal action verb + target factor)
 130:   2. shorter average path length to Success Factor(s)
 131:   3. higher influenceability of targeted factor(s)
 132:   4. alphabetical label
 133: 
 134: > [PROPOSED BLOCK - REVIEW ONLY - DETERMINISTIC SCORING INTERPRETATION]
 135: > Keep or adapt this block after a manual review.
 136: >
 137: > Deterministic scoring interpretation:
 138: > 1. Directly actionable by team:
 139: > - 1.0 if the team can implement without external dependency
 140: > - 0.5 if partial external dependency exists
 141: > - 0.0 if mainly external dependency
 142: > 2. Mechanism specificity:
 143: > - 1.0 if mechanism states clear action, target factor, and expected direction
 144: > - 0.5 if one of these components is missing
 145: > - 0.0 if mechanism is abstract or goal-like
 146: > 3. Measurable implementation state:
 147: > - 1.0 if a concrete binary or numeric metric is defined
 148: > - 0.5 if only qualitative metric is defined
 149: > - 0.0 if no measurable metric is defined
 150: > 4. Duplicate support penalty applies if proposed support targets the same factor(s) with no distinct mechanism statement.
 151: > 5. All scoring inputs and final score MUST be logged per support candidate.
 152: 
 153: > [PROPOSED BLOCK - REVIEW ONLY - TIE TOLERANCE]
 154: > Keep or adapt this block after a manual review.
 155: >
 156: > Tie tolerance:
 157: > If two support candidates differ by at most 0.01 in total score, apply tie-breakers in listed order.
 158: > If still tied after all tie-breakers, select alphabetical label.
 159: > The full tie-break trace MUST be documented in the IM derivation log.
 160: 
 161: **Step 4 - New/modified edge rule**
 162: - Every support-driven new or modified edge MUST be marked `[A]` until validated.
 163: - Each such edge MUST include mechanism, expected directional change, and validation plan in `attributes.description`.
 164: 
 165: **Step 5 - Minimal path preservation**
 166: - After support insertion and connection updates, at least one complete path from each Support to at least one Success Factor must remain.
 167: - Removing any selected Support must reduce at least one intended improvement path; otherwise support distinctness is not satisfied.
 168: 
 169: ### 3. Source Attribution (MANDATORY)
 170: 
 171: #### 3.1 Literature and Evidence (from Reference Model)
 172: - **INHERITED**: Literature sources `[1]`, `[2]`, etc. from Reference Model remain unchanged
 173: - **MANDATORY**: Source attribution for unchanged connections remains identical
 174: 
 175: #### 3.2 Assumptions for Interventions (Priority for new connections)
 176: - **MANDATORY**: All new connections (through Supports) MUST be marked as `[A]` (Assumption)
 177: - **MANDATORY**: `description` MUST contain justification of assumption:
 178:   - Theoretical foundation (design principles, methodology)
 179:   - Empirical evidence (pilot projects, expert opinions)
 180:   - Analogies to similar interventions
 181: - **GOAL**: Transform assumptions into evidence through incremental validation
 182: 
 183: #### 3.3 Validated Interventions (after piloting)
 184: - **ALLOWED**: After successful piloting, replace `[A]` with `[O]` (own investigation)
 185: - **ALLOWED**: With literature evidence, replace `[A]` with `[1-9]+`
 186: - **MANDATORY**: Document validation process in commit message
 187: 
 188: #### 3.4 Inadmissible Sources
 189: - **REJECT**: Connections with `[?]` (unknown source)
 190: - **REJECT**: New connections without source attribution (even if assumption)
 191: 
 192: ### 4. Measurability and Influenceability Criteria
 193: 
 194: #### 4.1 Support Properties
 195: - **EXPECTATION**: Supports have high influenceability (= 1.0)
 196: - **RATIONALE**: Interventions are under direct team control
 197: - **EXPECTATION**: Supports have measurable implementation state using discrete scale values (0, 0.5, 1.0)
 198: - **DOCUMENTATION**: Support implementation degree MUST be measurable (e.g., "Board present: yes/no", "Guide usage rate")
 199: 
 200: #### 4.2 Key Factor Changes
 201: - **HYPOTHESIS**: Supports improve Key Factors
 202: - **MANDATORY**: Expected improvement MUST be described in Support connection
 203: - **MEASURABILITY**: Key Factor measurability remains identical (from Reference Model)
 204: - **INFLUENCEABILITY**: Can increase if Support creates direct control option
 205: 
 206: #### 4.3 Success Factor Invariance
 207: - **MANDATORY**: Success Factor measurability and influenceability remain unchanged
 208: - **RATIONALE**: Long-term goals don't change through short-term interventions
 209: 
 210: ### 5. Connection Semantics
 211: 
 212: #### 5.1 Direction and Polarity
 213: - **MANDATORY**: All connections MUST be directed (`"direction": "directed"`)
 214: - **MANDATORY**: Connection type MUST use DRM polarities (`++`, `+-`, `-+`, `--`)
 215: - **EXPECTATION**: Support â†’ Key Factor connections are typically positive (`++`)
 216: 
 217: #### 5.2 Connection Descriptions for Supports
 218: - **MANDATORY**: Support connections MUST explain causal mechanism
 219: - **FORMAT**: "Support X improves Factor Y through Mechanism Z"
 220: - **LENGTH**: 30-200 words for new assumption-based connections
 221: - **CONTENT**:
 222:   - How does the support work?
 223:   - Why should it improve the factor?
 224:   - What assumptions underlie this?

 239: 8. **Assumption Trace Validation**:
 240:   - all new/modified support-driven edges marked `[A]`

 244: 1. **Reference Model Consistency**: Problem/Success Factor identical to Reference Model
 245: 2. **Support Integration**: All Supports connected to Key Factors

 247: 4. **Assumption Documentation**: All `[A]` connections have meaningful descriptions

 249: 6. **Minimal Path Preservation**: Support distinctness and intended improvement paths remain valid after pruning check

 321: ## Summary
 322: 
 323: Impact Models are future-state models that build on validated Reference Models. They:
 324: 1. Introduce **Support elements** (concrete interventions)
 325: 2. Document **new causal relationships** as **assumptions** `[A]`
 326: 3. Retain **Problem and Success Factor** from Reference Model
 327: 4. Follow an **incremental validation cycle**
 328: 5. Feed validated findings back into the **Main Model**
 329: 
 330: Impact Models are experimental in nature and enable systematic testing of design interventions with clear evidence basis.
